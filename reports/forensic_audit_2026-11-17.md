## 3. Risk-ranked findings and proposed cleanup

Labels describe proposals, not permission to change files. Every deletion requires separate approval, compatible regression tests and dependency review.

### P0/P1 — safety and recoverability

1. **REVIEW / DANGEROUS: active trades can fall outside the 100-row UI query.** `trading/trade_store.py:196-204` defaults `list_trades()` to the 100 most recently updated rows, including terminal trades. `service.py:694-718` uses it to select monitored symbols; `trade_manager.py:444-463`, `:465-491`, and `:3573-3589` use the same bounded list for ticks, startup recovery, and lifecycle reconciliation. An old nonterminal trade can be excluded when more than 100 newer rows exist, even if total open trades is low. Consequences may include missed conditional-entry evaluation, missing unprotected-price alerts or delayed lifecycle reconciliation. `list_non_terminal_trades()` explicitly avoids this limit (`trade_store.py:206-217`) for the BUY-block path, but substituting it throughout needs tests for semantics, scale, race/locking and ignored legacy states. This is a code-level risk, not evidence of a currently affected live position. Dependencies: monitor, tick handler, recovery, trade reconciliation. Do not delete any of these; add a >100-row disposable DB regression and separately approve a surgical fix.
2. **REVIEW / DANGEROUS: startup recovery and monitor run concurrently.** `service.py:587-591` independently schedules queue, reconciliation and market workers; `:767-775` awaits recovery inside the reconciliation worker, while `:734-755` can start the monitor/tick worker independently. The comment at `:772` asserts recovery occurs before ticks, but no ordering barrier is visible in these paths. Per-trade locking and state gates may mitigate particular interleavings; a harmful outcome has not been demonstrated. Existing wiring tests describe recovery before the first reconciliation sweep (`tests/test_service_live_wiring.py:1-9`), not necessarily a blocked-recovery/concurrent-tick schedule. Investigate deterministically before changing lifecycle behavior; deletion of locks or startup logic is unsafe.
3. **DANGEROUS / KEEP: live OCO and exchange child attribution remain unverified.** `docs/trading.md:825-829` explicitly says no live OCO from this repository was verified; `:736-742` describes incomplete child attribution and fail-closed behavior. Tests with fakes cannot establish live exchange guarantees. Keep `mexc/cli.py`, hybrid, all OCO state, child tracking, and evidence. Removing or simplifying these could compromise protection. A future owner-approved, non-invasive external verification plan—not an audit-time trade—is needed.
4. **REVIEW: fill sync is a protection gap under uncertain/missing evidence.** `_settle_entry_state` returns while `fill_sync_required` is set (`trade_manager.py:1044-1046`), and only then can place exits for known partial fills (`:1057-1064`). That avoids overselling from stale data but may leave acquired inventory unprotected while evidence is unavailable. Inspect escalation timing, recovery and visibility with injected prolonged `myTrades` failures; do not bypass fill proof. Its docstring (`:1028-1033`) incorrectly says exits only after terminal entry, conflicting with the actual partial-fill branch. Keep safety logic; correct documentation only after separate review.
5. **REVIEW: monitor failure does not stop ingestion.** `service.py:617-636,734-753` logs/returns when monitor construction/start fails; a start failure generates a critical event, but construction failure returns without that explicit event. This can leave conditional entries and unprotected-price alerts without ticks. Verify current operational alerting and add deterministic failure tests; no proof of production impact. Avoid changing to an unsafe global halt without policy review.
6. **REVIEW: migration 23 parks previous nonterminal trades and clears BUY-block state; migration 24 parks ambiguous old intents** (`db.py:1653-1689`). These are intentional owner decisions but can exclude historical orders from automatic management. Removing/re-running/reordering migrations or changing old records is DANGEROUS. Verify each supported upgrade from disposable snapshots; do not infer live state from migration text.
7. **REVIEW: credential-store cryptography is custom.** `control/secretbox.py:1-7,26-54,69-99` implements PBKDF2 plus HMAC-derived stream and encrypt-then-MAC; `_material` checks length, not actual entropy (`:26-38`). This is not proof of a cryptographic break; bespoke formats and weak human-selected keys merit specialist review. `control/store.py:277-305` and tests depend on the format. Removing or replacing it without versioned backwards-compatible key migration could lock out exchange credentials; DANGEROUS.
